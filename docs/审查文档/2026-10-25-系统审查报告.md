### 2.2 关键链路的数据流核查（重点）

**这是本次审查最重要的发现**：所有写操作（新增/改状态/置顶/编辑/删除）在成功后**都不主动更新本地状态**，UI 的更新完全依赖 Supabase Realtime 把变更推回来再触发一次整表重拉。

```
用户点击 → 调用仓储函数 → 数据库写入成功 → 【本地 state 不变】
                                        ↓
                       等待 Realtime postgres_changes 事件
                                        ↓
                          refresh() → getAllApplications() 整表重拉
                                        ↓
                                   列表才变化
```

由此产生的连带风险：

| 编号 | 风险 | 触发条件 |
|---|---|---|
| R-02 | 界面不更新，仅 Toast 提示成功，用户以为没生效并重复操作 | Realtime 未在 Dashboard 勾选该表、Realtime 断线、订阅失败（R-09） |
| R-15 | 每次写操作 = 1 次写 + 1 次 GET 全量，读写放大 2 倍 | 任何写操作 |
| R-01 | 重拉失败时把已有数据清空 | 网络抖动 / 离线 / 请求超时 |

**分组与排序的交互**：先按 `filterAndSort` 排好序，再 `buildBlocks` 按公司首次出现位置聚合。结果是"同一公司的多条记录被拉到首次出现的位置"，因此列表现次序 ≠ 纯排序结果。设计上可接受（避免同公司被拆页），但**排障时要记得这一点**，不要误判为排序 bug。

**问题**：
- **R-16**：单 chunk 552.98 kB，无 `manualChunks`。Supabase SDK + 两张主视觉 + 组件全部进同一桶。
- **R-16**：两张版画（598 kB 原始）**直接进首屏**且全部进入 precache。登录页其实只需要 `mucha-floral`，主界面只需要 `mucha-compass`，但当前都在初始包内。
- 首页 `<img>` 未设 `width/height` 与 `loading`，移动端存在 CLS 与解码抖动风险。

### 3.2 数据层

| 编号 | 问题 | 影响 |
|---|---|---|
| R-13 | `getAllApplications` 无 `limit`/`range`，一次拉回该用户全部记录；分页只在前端切 | 记录数 500+ 时首屏与每次回推都要传整表 |
| R-14 | Realtime 订阅未加 `filter: 'user_id=eq.<uid>'` | 服务端要为全表变更做 RLS 判定再广播 |
| R-15 | 任何变更触发整表重拉 | 写 1 条 = 多 1 次全量 GET |

### 3.3 渲染层

- **R-17**：`useApplications(all, opts)` 在渲染期直接调 `filterAndSort`，未 `useMemo`。每次父组件 re-render（输入关键字、Toast、抽屉开合）都会重跑一次 O(n log n) 排序 + O(n) 分组。
- `ApplicationList` 的 `buildBlocks` 已 `useMemo`，依赖 `rows` 引用；但 `filterAndSort` 每次返回新数组 → `rows` 引用恒变 → `buildBlocks` 实际每次都重算。
- **R-05**：`QuestionPanel` 渲染期调用 `URL.createObjectURL`，且从不 `revokeObjectURL`，每次选图/重渲染都会新增 Blob 引用，长时间使用会累积内存。

### 3.4 缓存与离线

- ✅ `runtimeCaching` 把 `*.supabase.co` 设为 `NetworkOnly`，避免读到脏数据。
- ✅ `registerType: 'autoUpdate'`，更新友好。
- ⚠️ 副作用：离线时数据请求全部失败 → 命中 R-01，列表变空。**PWA 目前只能"离线打开壳"，不能"离线看数据"**，与"可安装应用"的心理预期有落差。

### 3.5 性能结论

当前规模（个人使用、数十条记录）下体感流畅；瓶颈会出现在**记录数上百**以后，主要来自全量拉取与整表重拉，而不是渲染。优先级建议：R-01 > R-15 > R-13 > R-16 > R-17。

### 4.2 数据隔离（RLS 逐条核查）

```sql
-- applications
CREATE POLICY "own_applications" ON applications FOR ALL
  USING (auth.uid() = user_id);
```

| 表/策略 | 读写覆盖 | 结论 |
|---|---|---|
| `applications` `FOR ALL USING (auth.uid() = user_id)` | SELECT/UPDATE/DELETE 由 USING 过滤；INSERT 因未写 `WITH CHECK`，PostgreSQL 自动回落为 `WITH CHECK (auth.uid() = user_id)` | ✅ 无法读他人数据，也无法把行改成他人所有 |
| `question_records` `FOR ALL USING (auth.uid() = user_id)` | 同上 | ⚠️ **只校验了 `user_id`，没校验 `application_id` 是否属于自己**（R-08） |
| `storage.objects` insert/select/delete | `auth.uid()::text = (storage.foldername(name))[1]` | ✅ 路径首段强制为本人 UID，无法读写他人目录 |
| `storage.objects` update | 未定义 | ✅ 无需（上传用 `upsert:false`） |

**R-08 具体说明**：外键 `application_id REFERENCES applications(id)` 不会触发对被引用行的 RLS 检查。因此一个已登录用户如果知道（或猜到）他人投递记录的 UUID，可以把一条 `question_records` 挂到那条投递上。**能读的仍只有自己的数据**（SELECT 仍被 `user_id` 过滤），但会造成：
- 他人投递被写入脏关联数据；
- 他人删除该投递时，级联删除会带走这条脏数据（无声数据丢失）。

修复方式（二选一）：
```sql
-- 方案 A：策略层加归属校验
ALTER POLICY "own_questions" ON question_records
  USING (user_id = auth.uid())
  WITH CHECK (
    user_id = auth.uid()
    AND EXISTS (SELECT 1 FROM applications a WHERE a.id = application_id AND a.user_id = auth.uid())
  );

-- 方案 B：加复合外键
ALTER TABLE applications ADD CONSTRAINT applications_id_user_key UNIQUE (id, user_id);
ALTER TABLE question_records
  ADD CONSTRAINT fk_question_owner
  FOREIGN KEY (application_id, user_id) REFERENCES applications (id, user_id) ON DELETE CASCADE;
```

### 4.7 传输与响应头

- 部署在 Vercel，HTTPS 由平台默认提供 ✅

建议新增 `app/vercel.json`：

```json
{
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "X-Frame-Options", "value": "DENY" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
        { "key": "Permissions-Policy", "value": "geolocation=(), microphone=(), camera=()" },
        { "key": "Content-Security-Policy", "value": "default-src 'self'; img-src 'self' data: blob: https://*.supabase.co; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self' https://*.supabase.co wss://*.supabase.co; frame-ancestors 'none'; base-uri 'self'; form-action 'self'" }
      ]
    }
  ]
}
```

> 注：`style-src` 需 `'unsafe-inline'`（Tailwind 运行时写入 + 行内 `style={{backgroundColor}}`）；`img-src` 需允许 `blob:`（本地预览）与 `https://*.supabase.co`（签名 URL）。
